1）WPF 界面重构 + 一个静默丢包的 P0（11-05 深夜）

- Bug：`LiteService.PostAsync` 用 `JsonContent.Create(body)`，序列化延迟导致 `HttpClient` 退化成 `Transfer-Encoding: chunked`；而 `app.py` 的 `_read_json` 只读 `Content-Length`，chunked 请求被当成 `{}`。后果全静默：选项保存后滑块弹回、启动/结束动作不生效、其他任务批量执行失败、「继续未完成」实际重开一轮日常。

2）看门狗误杀长任务，P0（11-06 上午定位，当晚修）

- 现象：日常链 6 成功 2 失败，鸢报与收尾都在 150 s 被杀，但日志显示被杀时节点还在正常成功。
- 根因：`TaskerEventSink` + `Tasker.add_sink` 在 maafw 5.6.0 **只投递 `Tasker.Task.*`**，节点事件必须走 `ContextEventSink` + `add_context_sink`。因此 `_last_node_time` 永不刷新，`STALL_SECONDS=150` 退化成「任何任务超 150 s 必杀」，死循环守卫同时失效。
- 修法：`lite/session.py` 换 `ContextEventSink.on_node_pipeline_node` + `add_context_sink` / `remove_context_sink`；`test_round_progress.py` 改新接口并补回归用例。探针 A/B 验证过：A 通道只收到 `Tasker.Task.*`，B 通道收到节点事件。

3）退出时堆损坏 0xc0000374，P0（11-06 晚）

- 根因：`session.stop()` 为绕开原生析构卡死，手工调用 `obj.__del__()` 后丢弃对象；引用归零时 CPython 再跑一次 `__del__`，对已销毁句柄二次 destroy → 堆损坏，进程在写完「程序保持运行」后 3 秒消失。
- 修法：新增 `_release_native()`，析构后把 `_handle` 置空（maa 自己的析构本来就判 `if self._handle`）；顺带修「无 agent 时白等 3 s」。A/B：raw 模式报 `access violation`，fixed 模式干净通过。

4）活动页判页 + 鸢报批量收集等待，P1（11-06 晚，均已真机验证）

- 实施（`lite/pipeline_fixes.py`，`FIXES["start_日常鸢报启动"]`）：`确定批量收集小道消息.next = ["等待小道消息收集完成"]`；该等待节点 next = `[一键收取_小道消息, [JumpBack]小道消息收集中, 识别不可用的一键收取]`；`start_日常鸢报启动.next` 末尾追加 `end_鸢报四连完成`（DirectHit + next []），修掉「四个分支跑完必失败」。

6）内存构成实测 + 两项有效优化（11-07 上午）

- 逐层：解释器+`import maa` 35 MiB → 连模拟器 45（+10）→ 加载资源 119（+74，155 个 pipeline + 16 MiB 模板图）→ 首次 rec OCR 347（**+229**）→ 首次全屏 det OCR 540（**+193**）。**435 MiB 是 PP-OCRv4 两个模型的固定成本**（det.onnx 9.5 MB 膨胀 20×、rec.onnx 21 MB 膨胀 11×）。`debug_mode`、`save_draw`、识别图缓存全试过，对这部分无影响（差 13 MiB）；`ORT_DISABLE_MEMORY_ARENA=1` 也无效。
- `OMP_NUM_THREADS=4`：在 `_import_maa()` 里 import maa **之前** `setdefault`。onnxruntime 按 OpenMP 线程复制 CPU arena，16 核 → 4 线程后私有提交 1551→1095 MiB，而且**更快**（全屏 OCR 511 vs 544 ms/op）。这是最大单项收益。
- `Tasker.set_reco_image_cache_limit(64)`：默认 4096 帧，实测 200 次识别只涨 9.9 MiB（不是元凶），但按识别次数线性增长，留 64 帧更稳。

【三、必须接受的结论（别再重新论证）】

1. **内存口径统一用整棵进程树，并说明是否含 WPF 外壳。** 外壳实测空闲 140–148 MB RSS / 101 MB 私有，运行中 150–153 MB。11-07 早先公布的「峰值 798 MB」只算了 Python 服务，少算子进程 + 外壳约 240 MB（23%）。
2. **原版工作集 372 MiB 是换页假象，不是效率高。** 原版 155 个样本里 54 次单次变化 >40 MiB（最大 153），私有提交却恒定 2208 MiB —— 这是把模型页换到 pagefile、用时再换回，代价是 55% 单核 CPU。**「Lite 内存高 41%」的旧结论作废。** 正确说法：Lite 私有提交均值低 30%、峰值低 21%，CPU 18% vs 55%，磁盘 130 vs 985 MiB；只有工作集峰值更高（用内存换 CPU）。
3. **两个鸢报任务语义不同，不是一个任务。**「📜 鸢报四连 - 日常专用」(`start_日常鸢报启动`, `default_check: true`) 是日常链一环，每天只收一次菜，**完成语义 = 流程走完，与奖励是否到手无关**；气力不足时 `前往收集_小道消息.next` 首位是 `new不吃鸟食` 且其 next 置空 → 主动收手、不耗鸟食。「🔄 鸢报四合一」(`鸟食大礼包启动`) 才是循环任务，靠「自动吃鸟食」选项续跑。不要给日常版加「必须收到」判定或「未收取」告警文案。
4. **不量化 OCR 模型（用户 2026-11-07 明确否决）。** 量化版能把 435 MiB 压到约 120 MiB，但要重新验证识别率，风险不可接受。`assets/resource/base/model/ocr` 保持上游原样，不要再把「换/量化模型」作为降内存方案提出来。435 MiB 视为固定成本。
5. `stop` 是 `base.json` 里的正式节点（`DirectHit + StopTask`），不是占位符；`end_鸢报四连完成` 与它语义等价，但保留自造节点是为了挂 `focus`（`stop` 没有 focus 字段）。
6. `focus` 在 5.6.0 的 `NodePipelineNodeDetail` 里确实有值（字段：`task_id / node_id / name / focus`），已真机验证。

【六、会踩的坑（本轮踩过的）】

- 本地起服务**必须用后台任务**；`(cmd &)` 会在命令结束时被回收，端口随后返回 502。
- `runtime/last-run.json` 在 `POST /api/run-task` 后**不刷新**（mtime 不动），别拿它判断当前任务；以 `lite.log` / `runtime/debug/maa.log` 为准。
- `Task timeout [pretask.name=X]` + `invalid node id, handle error` 三连 = 该节点的 next 候选全部未命中 → 正常收尾，job 仍 succeeded，**不是失败**；`pretask.name` 是上一个完成的节点，不是超时对象。
- `task not found [node_name=...]` 出现在任务启动瞬间，是框架 apply override 前的预检自注入节点，无害。
- OCR `Wrong ocr_result size [boxes=[]]` 是 ROI 内无文字，常规噪声。
- 启动游戏早期 20 条 `correct_roi: roi is out of range [image.size()=[1280,720]]` 是横屏桌面截图 + 竖屏 ROI，预期内。
- 不要由 AI 工具启动/重启模拟器（沙箱会回收进程树并发 powerDown），只检测 `adb devices`；细节见 `AGENTS.md` R2 与 `docs/DEEPSEEK-HANDOFF.md`。
